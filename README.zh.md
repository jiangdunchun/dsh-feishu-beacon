[English](README.md) · **简体中文**

把 DeepSeek Harness agent 的进展，以及那些需要你回来的时刻，推送到飞书群。

长时间运行的 agent 有两个麻烦：你不想一直盯着它，但一旦走开，又会错过它「没有你就无法继续」的那些时刻。这个插件同时解决这两件事——agent 会主动把自己的里程碑报给一个你配置的飞书机器人，而提问、授权请求和失败则**无论 agent 是否记得上报**都会被推送。

```text
PROGRESS
Task: 修复不稳定的部署
Workspace: beacon-project
Time: 2026-09-21 14:20:03

第 2/4 步完成：问题出在重试定时器的竞态，不在部署脚本。
```

## 你会收到哪些通知

| 触发时机 | 收到什么 |
|---|---|
| agent 到达它认为值得告知你的里程碑 | 它自己写的内容，标题为 `PLAN`、`PROGRESS`、`DECISION` 或 `DONE` |
| agent 需要你的回答 | `DECISION` 卡片，正文首行为 `Answer needed`，包含每个问题与**每个选项及其说明** |
| agent 需要对敏感操作授权 | `DECISION` 卡片，正文首行为 `Authorization needed`，包含工具名与原因 |
| 一次运行失败 | `Turn failed`，包含错误信息 |

**卡片类型严格只有四种**——`PLAN`（任务拆解）、`PROGRESS`（完成关键步骤）、`DECISION`（需要你回到电脑前处理：做决定，或授权 agent 做不到的事）、`DONE`（交付了什么）。任何需要你动手的事都是 `DECISION`，无论它是提问还是权限请求；标题下方那一行会说明是哪一种。

`Turn failed` 是这四类之外的唯一一张卡片，它保留自己的颜色：一次跑挂的运行不是你能回答的决定，也不能被误当成决定。

每条都以**交互卡片**形式送达，标题栏颜色让你一眼看出是什么——也可以改成纯文本，见[关于「Message format」](#关于message-format)。

**运行成功时不会推送任何东西。** 如果你做完一件事、手机却毫无动静，那正是它在正常工作：每次运行都汇报是噪音，而这个插件存在的意义就是避免噪音。

**而且在你明确要求之前，它什么都不会推——一次只针对一个任务。** 你坐在电脑前时并不需要手机通知，而插件无法判断你是否已经走开——只有你自己知道。所以默认是静默的：只有在当前这段工作**被开启 watch** 时才会推送。见[观察一个任务](#观察一个任务)。

## 观察一个任务

watch 就是你的一句"我要让它自己跑，有事告诉我"。它由 agent 在你的指令里识别出这个请求后开启，任务结束时**自动关闭**，所以你永远不需要记得去关掉通知。

**用你自己的话开口就行，没有需要记住的关键词：**

> 我要出去一下，你做的过程中随时告诉我
> 我走开了，有进展就发我
> 每完成一步跟我说一声

agent 从你的指令里读出这个请求，并在它发出的第一条消息上打开 watch。**看起来像请求但其实不是**的情况：

| 不算请求 | 原因 |
|---|---|
| "模拟一个有交互的长任务" | "长"本身不是请求 |
| "修一下 dsh-feishu-beacon 这个插件" | 提到插件名是在谈论工具，不是在要求被告知这次的工作 |
| 在一个使用本插件的仓库里干活 | 仓库不是你的指令 |
| "接着之前那个继续" | 之前的请求授权的是之前的任务，不是这一个 |

**读这个意图是 agent 的事，插件不再用关键词去代替它判断。** 早先的版本要求你的指令里出现字面的 `beacon`，那个判定同时在两个方向上都错了：这个词就在本包的名字里，所以"修一下 dsh-feishu-beacon 这个插件"会授权一次通知；而任何机制都无法把这种"提及"和"请求"区分开。

插件仍然守住的是**后果**：一个 watch 只管一个回合，它是唯一能让消息发出去的凭据，而设置页里的开关优先级在它之上。

从被授权那一刻起：

| 你会收到 | 直到 |
|---|---|
| agent 上报的每一个里程碑 | 本回合结束 |
| 每一个需要你回答的问题 | 本回合结束 |
| 每一个授权请求 | 本回合结束 |
| 任务失败时的失败信息 | 本回合结束 |

**任务结束时，watch 随之结束。** watch 是为它被要求的那一个回合开启的，**回合边界就是它的到期时刻**——没有东西需要被关闭，也没有东西需要你记着。失败是这个回合能说的最后一句话，它会在控制权交还给你之前推送，所以"任务崩了"恰恰是仍然能到达你的那一条。

在任务中途回答 agent 提出的 decision，**不会**结束 watch。它还在做同一个任务，只是需要你先回一句。

watch 是 agent 做出的判断，不是插件替你按下的开关：agent 必须识别出你要求被持续告知，才会开启一个。这也是为什么同一回合里后来的一条指令**关不掉**它——回合边界是唯一的关闭点，agent 自己也无法在中途结束上报。

### 一个任务，一份授权

watch 的作用域是**一个任务——agent 交出控制权之前所做的那段工作**。你的下一条指令重新从静默开始，**即使上一个任务的 watch 从没被关闭过**，所以你永远不会因为一个"活过了头的 watch"而继续收到通知。下一个任务要收，就再说一次——用你自己的话。

## 开始之前

- 已安装 `dsh` CLI，并且有 **web** profile。
- 一个你有权限添加机器人的飞书群。

## 安装

```powershell
dsh plugin --profile web add dsh-feishu-beacon
```

然后**重启 harness**。设置页面只在启动时加载，所以正在运行的 harness 还看不到它。

## 配置步骤

### 1. 在飞书里创建机器人

飞书官方文档有完整的图文步骤——自定义机器人的设置入口在哪、如何复制 Webhook 地址、签名校验怎么工作：[自定义机器人使用指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN)。

简版步骤：

1. 打开你想接收通知的飞书群。
2. **设置 → 群机器人 → 添加机器人 → 自定义机器人**。
3. 起个名字，复制它给出的 **Webhook 地址**。
4. 如果机器人启用了签名校验，把 **签名密钥** 也复制下来。

### 2. 填进插件

打开 **设置 → Feishu beacon**，粘贴 Webhook 地址。地址必须以 `https://` 开头。如果你的机器人校验签名，把密钥也粘上；不校验就留空。

这里**没有保存按钮**——你输完即已写入，字段下方的状态行会告诉你是否生效。如果某个值被拒绝，它会留在输入框里并附上原因。

### 3. 点「Send test」

`Send test` 是页面上唯一的按钮。它会立刻用**页面当前显示的值**发一条消息，因此一次性证明三件事：地址对、密钥对、你的手机能看到这个群。这条消息一两秒内就会出现在飞书里。

如果页面报错，见[如果它不工作](#如果它不工作)。

### 4. 告诉 agent 去汇报

里程碑上报是 agent 自己的判断，所以需要你交代一次——用你自己的话：

> 我出去一下，你做的过程中随时告诉我

提问、授权请求和失败**不需要**你另外交代：只要 watch 开着，不管 agent 记不记得汇报，它们都会被推送。

## 可以调什么

全部都在同一个设置页上，而且**全部立即生效**，不需要重启任何东西。

| 设置项 | 作用 |
|---|---|
| **Enabled** | 总开关。关闭时完全不推送。 |
| **Notify on questions** | agent 需要你回答时推送。 |
| **Notify on approvals** | agent 需要授权时推送。 |
| **Notify on failed turns** | 运行失败时推送。 |
| **Title prefix** | 加在每个标题前面，用来区分不同机器/环境，例如 `[HOME-PC] PROGRESS`。 |
| **Host URL in messages** | 加一行 `Open at:`，指回你的 harness。详见下文。 |
| **Max characters** | 整条消息长度上限，默认 `3000`。超出部分会被截断并以 `...` 结尾。 |
| **Message format** | `card`（默认）或 `text`。详见下文。 |
| **Signing secret** | 仅在机器人校验签名时需要。 |
| **Webhook URL** | 机器人的 Webhook 地址。 |

三个通知开关是**故意独立**的：关掉一个不会影响另外两个。

两个凭据字段只显示 **stored** 或 **not set**，不显示值本身；只有在确实存了凭据时，旁边才会出现 `Clear`。你的 Webhook 和密钥保存在 harness 上，永远不会被发回浏览器。

### 关于「Message format」

消息以两种形式之一送达：**交互卡片**或**纯文本**。

- **`card`**（默认）——彩色标题栏、一行安静的元信息（任务与时间），然后是正文。颜色让你在读内容之前就知道这是什么：失败红色、待决橙色、完成绿色、计划与进展蓝色。
- **`text`**——全部挤在一个纯文本块里，也就是早期版本的形式。

**你不需要一次选对。** 用 `card` 时，如果你的群不接受交互卡片，插件会**把同一条消息改用纯文本重发**，所以格式问题绝不会让你丢掉通知。发生这种情况时 `Send test` 会告诉你——消息仍然送达了，但页面会说明卡片未被接受，你可以改成 `text` 不再尝试。

如果你就想要最朴素的形式，或者不想在卡片被拒时多发一次请求，那就选 `text`。

### 关于「Host URL in messages」

这个字段只控制一行——`Open at:`——其它什么都不影响。它的意义在手机上：飞书通知本身不携带任何会话信息，那一行就是你点回 harness 的入口。

- **在跑 harness 的同一台机器上看通知？** 留空即可。它会回退到 `DSH_WEB_URL`，harness 自己会设置。
- **在手机上看通知？** 回退值通常是 `http://127.0.0.1:<端口>`，这个地址在手机上指向手机自己，点了打不开。请填一个手机能访问的地址——同一 WiFi 用局域网 IP，外网用隧道/反代地址。

当这个字段和 `DSH_WEB_URL` 都没有设置时，这一行会被直接省略。

## 从 0.1.x 升级

**0.2.x 要求 dsh 0.2，0.1.1 要求 dsh 0.1.x——两者互不兼容。** 跑 dsh 0.2 就装 0.2.x；还在 dsh 0.1.x 就留在 0.1.1。

配置存放位置也变了：现在存在当前 profile 的 patch 层里，不再存于 `settings.yaml`。升级后请重新填入 Webhook 地址和签名密钥。

## 如果它不工作

**装完后设置里找不到这个插件。**
`dsh plugin add` 即使在安装失败时也会报成功，而没被登记为 bundle 的包永远不会加载。检查 `$DSH_HOME/profiles/web/package.json`，确认 `dsh-feishu-beacon` **同时**出现在 `dependencies` 和 `dsh.profile.bundles` 里。如果没有，重跑安装并留意 pnpm 的报错。最常见的原因是 `$DSH_HOME/profiles/web/pnpm-workspace.yaml` 里有个未决定的 `allowBuilds:` 条目——把它答成 `false`（对已发布的包来说构建脚本没有用），然后重新安装。

**「Send test」失败。**
确认 Webhook 地址以 `https://` 开头；如果机器人校验签名，确认密钥与机器人一致。页面上的 `502` 表示**飞书那边**拒绝了这条消息。

**我没收到通知。**
先看最可能的原因：你并没有要求过。上报是静默的，直到 agent 从你的指令里识别出"请持续告知我"，并且在任务结束时停止——所以一条你从没提过这个要求的任务什么都不会推，而仅仅提到本插件名也不会让它推。按顺序检查：你真的说了要被持续告知吗？然后确认这一次**应该**收到：运行成功是不会有任何推送的。再检查 **Enabled** 与对应的 **Notify on…** 开关。如果在 watch 开着时一次运行失败却没收到，那就是推送本身失败了——harness 日志里会有一条 **warning**，而绝不会是 error，因为推送失败不允许影响你的会话。

**agent 说没有 watch，所以不能上报。**
那是插件在拒绝一次没有 watch 的推送。它不是在要你换个说法：如果你想要上报，用你自己的话说明就行。

**通知收到了，但 `Open at:` 链接打不开。**
那个地址从你看消息的设备访问不到。见[关于「Host URL in messages」](#关于host-url-in-messages)。

**消息被截断了。**
超过 **Max characters**（默认 3000）就会截断。想接更长的内容可以调大，但请注意：手机上过长的消息反而没用，而手机正是这个插件的目标场景。

## 已知限制

- **回复不会回来。** 自定义机器人 Webhook 只能发。你无法在飞书里回答问题——消息会提示你回到 harness。
- **不会重试。** 一次失败的推送就是永久丢失。这也是为什么工具路径会把失败告诉 agent，而只有事件路径保持沉默。
- **极长会话可能重复收到同一条通知。** 去重是有容量上限的，超过之后会从头开始。
- **飞书必须能访问到 Webhook，你的 harness 也必须能访问飞书。** 企业网络只要挡住任一方向，消息就会静默丢失——依赖它之前先用 `Send test` 验证。

## 卸载

```powershell
dsh plugin --profile web remove dsh-feishu-beacon
```

这会把包移除，但**不会**把它的名字从 profile 的 bundle 名单里删掉：dsh 只在**安装时**协调 `dsh.profile.bundles`，所以卸载会留下那个名字，下次启动就会尝试加载一个已经不存在的 bundle。请打开 `$DSH_HOME/profiles/web/package.json`，把 `"dsh-feishu-beacon"` 也从 `dsh.profile.bundles` 里删掉，然后重启 harness。

你的 Webhook 地址与签名密钥仍留在 profile 的配置文件（`cordis.patch.yml`）里。如果想让它们一并消失，把那行也删掉。

## 给开发者

以下内容关于插件本身的开发。

├── README.md             英文版
├── README.zh.md          中文版（本文件）
├── lib/
│   ├── index.js          宿主半：传输、事件层、工具、Config、路由
│   └── client.js         客户端半：设置页面
└── test/
    ├── smoke.mjs              宿主冒烟测试
    ├── client-smoke.mjs       客户端契约测试
    ├── no-cjk.mjs             零 CJK 强制检查
    ├── cordis-mount.mjs       真实注册表挂载检查
    ├── install-load.mjs       已安装 profile 加载检查
    ├── live-contract.mjs      运行中 harness 契约检查
    ├── pack-install-check.mjs 发布清单打包检查

只有 `lib/`、`cordis.patch.yml`、两个 README 和 `LICENSE` 会随包发布；`test/` 下的一切都留在仓库里。用 `npm pack --dry-run` 核对。

所有面向用户和面向模型的字符串都集中在两半各自的 `MESSAGES` 块里，因此翻译或把某个标签做成可配置，只需要改一处。

### 工作原理

两层，缺一不可：

- **工具层。** 只有模型自己能分辨「测试刚通过」和「架构已定稿」，所以里程碑上报是一个工具 `dsh_beacon`，由模型主动调用。参数是 `message` 和可选的 `kind`（`plan`/`progress`/`decision`/`done`，就是全部四类）。
- **事件层。** 工具只在模型记得调用时才触发，而 `ask_user_question`、`approval/asked` 和失败的 `turn/end` 恰恰是用户必须回到电脑前的时刻。这三类由会话事件推送，与模型是否记得无关，并且渲染成同一套四类：提问与授权请求都是 `DECISION`（两者都需要你回到电脑前），正文首行说明是哪一种；只有 `Turn failed` 保留自己的标题与红色，因为它不是你能回答的决定。

推送的授权是 **agent 自己的 `watch: true` 调用**，插件守住的是它的**后果**，而不是回头去读谁说了什么：`lib/index.js` 从会话日志里折叠出两件事——有没有记录过 watch、它记在哪个回合。插件**不再读取用户消息**；判断"这是不是一个请求"是 agent 的工作，提示词里写明了这一点，也写明了本包自己的名字不算请求。

早先的版本改为检测用户指令里那个字面的触发词。那个判定同时在两个方向上都错了：这个词就在 `dsh-feishu-beacon` 里，所以"修一下 dsh-feishu-beacon 这个插件"会授权一次通知；而任何机制都无法把这种"提及"和"请求"区分开。它已经被移除，留下的只有按回合生效的 watch。

让授权到期的是**回合比较**，而且它是唯一的到期机制：回合结束时没有任何东西写入 session。这不是省事——dsh 拒绝在发布追加的过程中再次追加，而 `turn/end` 观察者正是在发布过程中运行的，所以那条"关闭"事件永远落不了盘；它在真实会话里就没落盘，于是 watch 越过了自己的回合，工具看到会话上已有 watch 便不再为下一个回合开启，随后又拒绝推送，第一个任务之后的一切都被判为未授权。因此规则是"当前正在跑的这个回合有没有 watch"，从来不是"这个会话有没有被 watch 过"。

插件导出一个 `Config` schema（每个字段都是 `.volatile()`，只有 `format` 例外），并通过 `ctx.settings.update` 写回；Loader 会用该 schema 解析这一行的配置并交给 `apply`，每次编辑后重新执行 `apply`。配置有两层，后者覆盖前者：`cordis.patch.yml` 的 `config:` 块，然后是 `$DSH_HOME/profiles/<profile>/cordis.patch.yml` 里这一行的 `config:`。

设置页面通过两条 HTTP 路由通信：`/api/dsh-feishu-beacon/config`（`GET` 脱敏视图，`POST` 补丁）与 `/api/dsh-feishu-beacon/test`（`POST` 一条测试消息）。`POST` 的请求体就是配置补丁：普通字段合并写入，`clearWebhook` / `clearSecret` 清除已存凭据，而空的凭据字符串表示「保留已存的值」。

`webhookUrl` 与 `secret` 声明为 `role("secret")`，因此 dsh 会把它们从所有面向网络的视图中剥离。由于「空」和「未设置」是两种不同的存储状态，清除走的是声明式 `unset`，而不是写入空字符串。

三个飞书细节如果在实现时弄错会**静默失败**：信封（`msg_type: "text"`、`content.text`）、成功码（缺失代表成功，存在且非零代表失败）、签名（以 `"<timestamp>\n<secret>"` 为 HMAC-SHA256 密钥、消息体为空、摘要为 base64）。其它聊天平台这三者都不同，所以「改一下 URL 就能用」是错的。

### 发布

`.github/workflows/publish.yml` 使用 npm 的 **trusted publishing**（OIDC）：这个仓库不存在长期有效的 token，npm 会用包页面上配置的 trusted publisher 来校验 workflow 的短期身份。手动触发该 workflow 即可，只想想看 tarball 就用它的 dry-run 输入。

如果你手动发布，注意两个坑：

- 暂存（staged）版本会**阻塞**同版本号的直接发布，而清除暂存需要 WebAuthn 安全密钥。此时抬高版本号是出路。
- npm registry 可能需要几分钟才让新版本可见。发布报成功但 `npm view` 还看不到，并不等于失败——过一会儿再查。

### 变更记录

#### 0.2.5

**上报重新交给 agent 判断，关键词取消了。** 指令里不再需要出现 `beacon`：agent 从你的话里读出你是否要求被持续告知，并用它发出的第一条消息打开 watch。被它替换掉的字面判定同时在两个方向上都错了——这个词就在本包的名字里，所以"修一下 dsh-feishu-beacon 这个插件"会授权一次通知；而任何机制都无法把这种"提及"和"请求"区分开。插件仍然守住后果：一个 watch 只管一个回合，它是唯一能让消息发出去的凭据，设置页里的开关优先级在它之上。工具会拒绝任何需要 watch 却没有 watch 的调用，所以静默仍然是默认状态。见[观察一个任务](#观察一个任务)。

两个值得说明的后果：插件**完全不再读取你的消息**，所以授权不再依赖任何事件名，也不依赖排队中的指令被识别；另外，同一回合里后来的一条指令**关不掉** watch——回合边界是唯一的关闭点，agent 自己也无法在中途结束上报。

#### 0.2.4

**破坏性变更：只有当你自己的指令里出现 `beacon` 这个词时，才会推送。** 现在每一次推送都由这**一个字面的词**把关，判定由**插件**执行而不是由 agent 自行判断，并且授权在任务结束时失效。你坐在电脑前时手机通知就是噪音，而插件无法判断你是否已经走开——只有你自己知道，所以它不再猜。**升级后插件会保持静默，直到你为某个任务说出那个词。** 见[观察一个任务](#观察一个任务)。

**推送的卡片严格只有四类：`plan`、`progress`、`decision`、`done`。** 事件层也走这四类，不再自带标题。提问与授权请求都是 `DECISION`——两者都需要你回到电脑前——由正文首行（`Answer needed`、`Authorization needed`）说明是哪一种。在此之前它们被当作 `PROGRESS` 推送，这也意味着 0.2.3 说明里的颜色从未生效：授权请求到手机上是蓝色，失败也是蓝色。`Turn failed` 仍然单独成卡，并且现在真的是红色，因为跑挂的运行不是你能回答的决定。

**两个门控缺陷，都导致第一个任务之后再也推不出去。** watch 在它所在的回合结束时就作废，但工具问的是"这个会话有没有过 watch"，而不是"当前回合有没有 watch"，于是第二个任务里它不肯开 watch、随后又拒绝推送——你要求被告知的第二个任务，成了你最后一个能被告知的任务。另外，原本要在 `turn/end` 观察者里往 session 追加一条关闭事件，而 dsh 明确拒绝在发布追加的过程中再次追加（"session append cannot reenter while another append is being published"），所以那次关闭从未落盘。现在**回合边界就是关闭**，直接从日志位置读出，观察者不再写入 session。

另外：用户指令现在按 `user/message` 读取——dsh 0.2 实际发出的事件类型。此前只找 `message/user`，而它从未出现过，所以授权实际上一直依赖回退路径。

说出那个词就开启 watch，任务结束时它自动关闭，也就是 agent 把控制权交还给你的时候。在任务中途回答 decision 不会结束它：agent 还在做同一件事，只是需要你先回一句。

失败会在 watch 关闭**之前**推送。这个顺序正是关键：任务崩了恰恰是你走开时最需要知道的事，先关闭就会把它吞掉。

工具可以开启 watch 并上报，但**永远不能关闭**。一个"体贴地"替你停止通知的模型会让你在沉默中干等，所以关闭权只留给你。

字面判定替换了本版本早期的一个做法：那时把决定权留给了 agent。那不够好——某个会话里用户只说了"模拟一个有交互的长任务"，agent 就推断"这个任务是为了测试本插件"，于是自行开启上报并推了四条没人要求的通知。**一条模型能推理绕过的规则不算规则**，所以判定移进了插件。

另一半规则不是强制而是**沉默**：agent 不许在你没提的情况下提起这件事，包括在它决定不调用工具的那一轮里用正文写出来。这个故障被实际观察到过——agent 的推理是"用户这次没提 beacon，所以我不提它"，然后它的回复正是以那句话开头。这条禁令由 `systemPrompt` 段落承载，每一轮都会装配。

`/beacon` 命令被**禁用**：命令会绕过这条规则所依赖的那种识别。

#### 0.2.3

消息默认以**交互卡片**发送：带颜色的标题栏标明事件类型，一行安静的元信息，然后是分隔线与正文。颜色是关键——失败红色、待决橙色、完成绿色、进行中蓝色——让你在读内容之前就知道这条通知是什么。

新增 **Message format** 设置，可选 `card` 或 `text`。`text` 恢复原来的纯文本形式。**卡片被拒时会自动回退为纯文本**，所以不接受卡片的群依然能收到每一条消息；发生回退时 `Send test` 会说明。

**Max characters** 默认值改为 `3000`（原 `1800`），因为卡片能承载更多内容才开始影响手机上的可读性。

卡片正文是 markdown，因此模型自己的标点会被转义——里程碑里一个不配对的 `**` 否则会吞掉消息剩余部分。
